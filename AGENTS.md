# Instructions for Codex

- Inspect git status, relevant source, dependencies, configuration, migrations, tests and existing guidance before editing. Preserve unrelated staged, unstaged and untracked work; never reset or silently rewrite it.
- Read [PLANS.md](PLANS.md) and the relevant [product and engineering documents](README.md#documentation) before significant work. Distinguish observed implementation, accepted direction, proposals and hypotheses. Record conflicts with user-authored decisions; do not silently supersede them.
- Reuse established conventions and dependencies. Keep changes scoped to the requested outcome. Do not scaffold speculative features or introduce infrastructure without a demonstrated requirement. Update affected documentation when behavior or decisions change.
- Enforce authentication and object-level authorization on the server. Derive the acting user from trusted authentication, never a client-supplied owner ID. Deny access by default; test cross-user access and privileged actions. Keep secrets and sensitive application/report data out of responses and logs.
- Give each domain module ownership of its state and invariants. Use explicit services for cross-module changes; avoid shared mutable entities and direct writes to another module's persistence. See [DOMAIN.md](docs/DOMAIN.md) and [ARCHITECTURE.md](docs/ARCHITECTURE.md).
- Protect integrity with validation, database constraints and transactional service operations. Define legal transitions before implementing them. Handle concurrent acceptance, withdrawal, capacity changes and duplicate requests explicitly; use locking/version checks and idempotency where retries could duplicate effects. Do not claim these mechanisms exist before implementation.
- Use Flyway for schema changes and Hibernate validation. Inspect migration history before editing migrations, especially the currently empty V1. Never rewrite an applied migration; prefer additive, compatible migrations. Plan backfills, rollout and recovery for destructive changes; require explicit authorization for data destruction.
- Add meaningful tests appropriate to behavior: unit tests for rules, PostgreSQL integration tests for persistence/transactions/concurrency, and authorization tests for protected flows. Use JUnit; consider Testcontainers when database tests are introduced. Do not add tests that merely repeat implementation details.
- Run scoped validation appropriate to the change. Report exact commands, outcomes and any checks not run; never imply a build, deployment or feature is verified from file presence alone. For documentation, check links, consistency, git diff --check and final git status.
- Keep [PLANS.md](PLANS.md) current with evidence for completed gates, remaining risks and one next task. Report changed files, behavior, validation and material limitations.
- Do not commit, push, deploy, rotate credentials or change external services without explicit user authorization. Do not expose credentials. Stop at the requested scope; documentation work does not authorize implementation.
